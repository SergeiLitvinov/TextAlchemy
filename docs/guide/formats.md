## Первый срез HTML-импорта


Статус 2026-09-13: реализован и проверен на tests/corpus/scientific-html.html. Это семантический импорт статического документа; режим faithful для входного HTML не предлагается.

Граница реализации: статический локальный HTML с заголовками, абзацами, вложенными списками, таблицами, ссылками, изображениями data URI, встроенными SVG и MathML. Порядок содержимого сохраняется в DocumentModel; модель можно изменить и экспортировать в HTML/DOCX. Неподдержанные свойства должны попадать в отчёт, а не обозначаться как отсутствие потерь.

CSS: internal style и inline style; селекторы тега, класса, ID, их сочетания и универсальный селектор; специфичность, порядок и !important. Наследуются цвет, гарнитура, размер, начертание, выравнивание и white-space. Семантические strong/em и заголовки задают начальные значения, которые CSS может переопределять. Сложные селекторы, внешние таблицы, @media/@page, flex/grid, позиционирование, псевдоэлементы и печатная пагинация вне этого среза и диагностируются. Парсер синтаксиса — [tinycss2](https://doc.courtbouillon.org/tinycss2/stable/api_reference.html).

Импорт не выполняет JavaScript и не загружает сетевые ресурсы. Относительные файлы изображений доступны только при явном resource_root в Python API; обычная конвертация CLI/Web принимает самодостаточный HTML и сообщает о пропущенных файлах. Это исключает чтение соседних загрузок на сервере. Ссылки HTTP(S), mailto и внутренние якоря сохраняются как ссылки. SVG/MathML очищаются от активного содержимого и внешних обращений.

Установка дополнительных компонентов: uv sync --extra html (для DOCX также --extra docx). Полный набор по-прежнему устанавливается через uv sync --all-extras.

Критерии приёмки: фиксированный научный пример проходит HTML → JSON → HTML/DOCX; тесты проверяют порядок и текст, независимые CSS-ожидания, содержимое таблицы/списков, ресурсы и формулы после изменения модели. Отдельно проверяются диагностика неподдержанного CSS и ресурсов, отказ строгого бюджета при потерях, доступность маршрута в Web и работа без необязательных зависимостей.

### Использование

```powershell
uv run textalchemy convert-file input.html model.json --json
uv run textalchemy convert-file input.html result.docx --json
# Для повторного экспорта HTML через модель (прямой HTML → HTML копирует файл):
uv run textalchemy convert-file model.json result.html --json
```

Python: textalchemy.formats.html.read_html_model(path, resource_root=None). Операция конвейера extract.html_model принимает Document именованным параметром doc. Простое извлечение текста поддерживает HTML через extract.text. В Web HTML/HTM доступны в общем каталоге с пояснением ограничений.

Импортные ограничения хранятся в metadata.html.warnings и добавляются как LOSS в отчёт маршрута html.model. При строгом бюджете max_loss_issues=0 результат с потерями не публикуется, прежний файл сохраняется. В отдельном JSON модели предупреждения остаются метаданными; самостоятельный экспорт уже сохранённой модели сообщает о своих потерях, не переоценивает исходный HTML.

[Датированные результаты приёмки](../history/html-acceptance.md).

Ограничения: селекторы с комбинаторами, псевдоклассы/элементы, background-color, размеры/адаптивный выбор img, особые типы/обратная нумерация и многоабзацные пункты списков диагностируются. Вложенные списки обычной структуры поддерживаются. Rowspan хранится в модели/HTML, но DOCX пока сообщает о неподдержанном вертикальном объединении. Якоря на абзацах/заголовках поддержаны; строчные якоря диагностируются. CSS геометрия, внешние stylesheets и точная пагинация остаются за границей среза; отсутствие LOSS не является измерением визуального совпадения страниц.

### Переход от предупреждения к фрагменту

В Web предупреждения импорта HTML содержат кнопку перехода в инспектор. Он показывает текст импортированного блока (первые 1200 символов) и подписи/адреса изображений; это структурный фрагмент, без воспроизведения оформления страницы. Изображение без подписи, которое не удалось загрузить, оставляет пустой абзац с привязкой и сведениями об источнике. Повторяющиеся ошибки в разных блоках имеют отдельные ссылки. Общие правила, например @page, открывают область «Весь документ».

Технический контракт: `properties.html.block_id` у импортированных блоков совпадает с `location` предупреждения в `metadata.html.warnings`. Краткие снимки адресуемых фрагментов находятся в `metadata.html.locations` и в `report.metrics.step_metrics["html.model"].html_locations`. Эти данные сохраняются через JSON модели и дисковое хранилище Web-задач. Идентификаторы не зависят от имени файла и пользовательских HTML-якорей; устойчивость после изменения структуры исходника и нового импорта не обещается. Снимки отражают момент импорта, а не последующие произвольные правки модели.

Неподдержанное объявление в допустимом CSS-селекторе диагностируется для блоков, к которым селектор применяется. Неподдержанные селекторы и общие правила диагностируются для документа. При отсутствии соответствующего импортированного блока используется общая область.

Приёмка: `tests/corpus/html-warnings.html` → DOCX в Chromium при ширине 375 и 1280 px. Проверены выбор CSS/ресурсного предупреждения, текст соответствующего фрагмента, клавиатурный переход к общей области, перенос фокуса и очистка инспектора при следующей конвертации. Регрессии проверяют JSON, сохранённую Web-задачу, повторяющиеся ошибки, таблицы и изображение без alt. Редактирование CSS/документа и визуальное выделение на странице в этот срез U1 не входят.

## Текстовый маршрут


`convert-file model.json result.txt` сохраняет основной текст модели в UTF-8 без BOM, с переносами LF. Тот же маршрут доступен через Web и операцию `render.txt_model` (параметры `document` и `output_path`, результат — отчёт).

Для проверки обратного пути используйте TXT → модель → TXT: прямой TXT → TXT является тождественным маршрутом. Пустые абзацы, пробелы, табуляция и конечный перенос сохраняются. Входной cp1251 декодируется импортёром, выход всегда UTF-8; исходная кодировка и CRLF не восстанавливаются.

Абзацы и секции разделяются переносом строки, ячейки таблиц — табуляцией. Многострочные и вложенные ячейки выводятся текстом: это не обратимый табличный формат. Для формул используется текстовая альтернатива либо исходная запись, для изображений — альтернативный текст. Колонтитулы не включаются в основной текст. Оформление, ссылки как интерактивные объекты, геометрия и ресурсы не сохраняются; потери отражаются в отчёте. Режим максимальной визуальной точности не предлагается.

Запись атомарная. Тесты проверяют изменения модели через два цикла сохранения, Unicode и пустые строки, диагностику упрощения, ошибку записи, CLI, операцию пайплайна и доступность направления в каталоге Web.

<a id="epub"></a>
## Импорт EPUB в редактируемую модель


Маршрут `epub.model` читает главы в порядке spine и создаёт отдельную секцию для каждой линейной главы. Он доступен через `convert-file`, Web и операцию `extract.epub_model`. Навигационный XHTML не становится пользовательской главой; заголовки берутся из оглавления, а при его отсутствии — из первого заголовка главы.

Абзацы, заголовки, элементы списков, цитаты, pre и подписи становятся редактируемыми абзацами. Сохраняются пустые абзацы, inline-изображения, внешний URL и внутренние ссылки. Межглавные ссылки нормализуются в стабильные HTML-якоря, поэтому EPUB → HTML создаёт рабочие переходы внутри автономного результата.

Растровые изображения и SVG сохраняются ресурсами модели вместе с исходными байтами и provenance. Подключённые CSS-файлы также сохраняются как вложения. Базовый каскад материализует шрифт, размер, цвет, фон, жирное/курсивное/подчёркнутое и верхний/нижний индекс из inline-стилей и простых селекторов `tag`, `.class`, `#id`, `tag.class`. Поддерживаются размеры pt, px, em/rem и проценты.

Сложные селекторы, псевдоклассы, CSS variables, media queries, generated content, layout и точная пагинация пока не вычисляются. Отсутствующие изображения перечисляются в `metadata.epub.warnings`. Исходный EPUB не собирается обратно: настоящий обратный путь сейчас проходит через редактируемую модель в HTML, DOCX, PDF, PPTX или TXT.

Тесты проверяют порядок глав, оглавление, внешние и межглавные ссылки, CSS cascade, inline-стиль, изображения и CSS-ресурсы, provenance, JSON round-trip, pipeline, Web-каталог и автономный HTML.

## Редактируемый экспорт PPTX


Линии тренда и планки погрешностей сохраняются нативно через `series[].trendline` и `series[].error_bars`. Тренды поддерживают `linear`, `exp`, `log`, `poly` (порядок 2–6) и `power`, а также `movingAvg` (период 2–255). Для трендов, кроме скользящего среднего, можно включать `show_equation` и `show_r_squared`. Расчёт выполняет офисная программа.

Параметры `forward` и `backward` задают неотрицательную конечную длину прогноза вперёд/назад для всех поддержанных типов, кроме `movingAvg`. Дробные значения и ноль сохраняются. `intercept` задаёт пересечение для `linear`, `poly` и `exp`; для экспоненциального тренда требуется положительное значение, для линейного и полиномиального допустимы ноль и отрицательные значения. Единицы и расчёт прогноза определяет офисная программа в соответствии с типом диаграммы. Эти параметры независимы у нескольких трендов; удаление ключа возвращает стандартное поведение. В HTML тренд с любым из этих параметров пропускается с потерей `chart-trendline`: расчёт прогноза/фиксированного пересечения там пока не реализован.

Поле `trendline` принимает одиночный объект либо список до 64 объектов. Каждый тренд может иметь строковое `name`; типы, параметры, цвета и флаги отображения независимы. Список сохраняет порядок, в том числе при одинаковых типах трендов. При чтении одной линии возвращается объект, нескольких — список. Удаление элемента списка удаляет соответствующую линию при экспорте; удаление всего ключа убирает все тренды. Пустой, чрезмерный или некорректный список отклоняется целиком с диагностикой, при этом ряд и его погрешности сохраняются. HTML-рендерер обрабатывает все элементы списка в рамках уже поддерживаемых им типов трендов.

Погрешности поддерживают `value_type`: `fixedVal`, `percentage`, `stdDev` с неотрицательной конечной величиной `value` и `stdErr` без величины. `bar_type` задаёт `both`, `plus` или `minus`; `direction` — X/Y для XY и пузырьковых диаграмм, Y для вертикальных столбцов/линий/областей, X для горизонтальных столбцов. Для обоих объектов поддержан непрозрачный сплошной RGB-цвет (`color_value` приоритетнее `color`). Настройки независимы для рядов комбинированных диаграмм; удаление ключа убирает объект при следующем экспорте.

Для двух независимых направлений XY/пузырькового ряда `error_bars` принимает список из двух объектов с `direction="x"` и `direction="y"`. Величины, типы, массивы, цвет и режим plus/minus независимы. Старый одиночный объект сохраняет поддержку; при чтении одного направления возвращается объект, двух — список в порядке XML. Дубликаты, более двух направлений и неверная настройка любого элемента отклоняют весь набор с диагностикой. Чтобы удалить одно направление, удалите соответствующий элемент списка. Категориальные диаграммы принимают только одно направление. Обработчик погрешностей HTML выбирает настройки соответствующей оси; это не расширяет поддержку самих типов диаграмм HTML-экспортёром.

Пользовательские погрешности задаются как `value_type="cust"` с массивами `plus`/`minus`, длина которых равна числу точек ряда (до 100 000). Для режима `both` обязательны оба массива; для `plus` либо `minus` — соответствующий массив. Элементы — конечные неотрицательные числа или `null` для пропуска, ноль сохраняется как число. Индексы и хвостовые пропуски сохраняются через `ptCount`/`pt idx`. Экспорт использует нативные числовые массивы `numLit`; импорт `numRef` использует кэш значений, без переноса формулы и связи с ячейками книги. Без кэша необходимые массивы не восстанавливаются, и экспорт сообщает о потере. HTML-предпросмотр учитывает разреженные массивы и односторонние погрешности.

Неподдержанные или неверные настройки статистического объекта отклоняются целиком с потерей `charts`; основной ряд сохраняется. Пока не переносится сложное оформление подписи тренда. Тренды накопительных рядов отклоняются. Проверки всех перечисленных вариантов статистики структурные; их полная визуальная приёмка в Office остаётся открытой и не входит в принятую ниже проверку двух презентаций. Формат нативного объекта описан в [документации Microsoft](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.charts.trendline?view=openxml-3.0.1).

Модель документа можно сохранить как презентацию через `convert-file`, Web-конвертер или операцию `render.pptx_model`.
Каждая секция становится отдельным слайдом. Все слайды имеют размер первой секции; автоматической разбивки длинного текста на слайды пока нет.

### Граница HTML-предпросмотра и приёмка

Нативный PPTX и HTML имеют разное покрытие статистики диаграмм. HTML пропускает log/power и неизвестные типы тренда с LOSS chart-trendline и lossless=false; линейная подмена не используется. То же относится к прогнозу и заданному пересечению. Наличие ветвей linear/movingAvg/exp/poly не означает независимой приёмки всей их численной и визуальной семантики Office.

HTML-планки stdDev учитывают множитель value, включая ноль; текущий расчёт отклонения использует делитель N. Численные регрессии проверяют координаты на известном наборе данных. Этот результат не расширяет покрытие типов диаграмм.

Ограниченный editable-срез принят в PowerPoint на двух презентациях корпуса: [границы и результаты приёмки](../history/pptx-acceptance.md). Исправлены цвет текста из fontRef, превращение textbox в автофигуру и добавление отсутствующих эффектов темы. Остаточное упрощение темы таблицы, оформления диаграммы и градиента фигуры диагностируется. Эта таблица является единственным статусом приёмки; остальные описания возможностей не означают проверки всех объектов в Office.

### Проверка обратного пути

```powershell
uv run textalchemy convert-file source.pptx model.json --json
# Измените текст, геометрию или данные объектов в модели.
uv run textalchemy convert-file model.json result.pptx --json
```

Прямая конвертация PPTX → PPTX считается тождественным маршрутом: для проверки импортёра и экспортёра используйте промежуточную модель.
Python API: `textalchemy.convert.write_pptx_model(document, output_path)` возвращает отчёт о потерях.
Операция `render.pptx_model` возвращает сериализуемый отчёт с путём результата, а не только путь: предупреждения остаются доступны в отчёте пайплайна.

### Что сохраняется

- Текстовые блоки и стандартные автофигуры, координаты и поворот; шрифт, размер, основные начертания, RGB-цвет и внешние ссылки.
- Настройки абзацев текстовых фигур: списки, начальный номер, уровни, отступы, интервалы, отдельное выравнивание абзацев, поля и вертикальное положение текста. Мягкий перенос не превращается в новый абзац. Наследуемые настройки txStyles/lstStyle материализуются в модели; локальное начертание не сбрасывает унаследованный шрифт.
- Явные позиции и выравнивание табуляции, стандартный шаг табуляции, направление текста и режимы автоподбора (выключен, уменьшение текста, рост фигуры), включая сохранённые коэффициенты уменьшения. Настройки доступны для изменения через модель как у текстовых фигур, так и у ячеек таблиц. Их применение при отображении выполняет офисная программа; экспортёр сам не рассчитывает новый размер шрифта или фигуры.
- Настройки геометрии автофигур и произвольные DrawingML-контуры; прямые, ломаные и кривые коннекторы, наконечники и штриховка. Привязки к фигурам переназначаются на новые идентификаторы; удалённые и неоднозначные цели диагностируются, а не подменяются другим объектом.
- Вложенные группы и порядок наложения объектов. Трансформации групп нормализуются в абсолютную геометрию дочерних объектов; повороты и отражения сохраняются. Правки рамки объекта в модели учитываются при экспорте.
- Таблицы с объединениями ячеек, ширинами колонок и высотами строк. В ячейках сохраняются отдельные абзацы (включая пустые), форматирование фрагментов, ссылки и мягкие переносы; явные сплошные заливки, отсутствие заливки, поля, вертикальное выравнивание и границы, включая края объединённых ячеек.
- Категориальные столбчатые, линейные, круговые, кольцевые диаграммы и диаграммы с областями — с встроенной книгой данных. Накопительные и нормированные варианты сохраняют тип, а пропуски в рядах — исходные позиции.
- Точечные XY (с линиями/сглаживанием/маркерами) и пузырьковые диаграммы: независимые координаты и размеры пузырьков, в том числе в редактируемой встроенной книге. Сохраняются основные шкалы, заголовки осей, логарифмическое основание, обратный порядок и формат чисел.
- Комбинированные диаграммы из вертикальных столбцов, линий и областей с общей книгой данных, отдельными типами/группировкой рядов и вторичной числовой осью. Значения и привязку ряда к шкале можно менять через модель; пределы, единицы и заголовки основной и дополнительной шкалы сохраняются независимо.
- Комбинации горизонтальных столбчатых наборов: обычные, накопительные и нормированные, с общей либо дополнительной числовой шкалой сверху. Сохраняются отдельные наборы и встроенная книга; изменения значений проверены после двух циклов JSON/PPTX.
- Растровые изображения, обрезка и альтернативный текст; SVG как векторный ресурс, с растровым превью при его наличии.
- Корректные OMML-формулы, базовые формулы MathML (дроби, корни, индексы, степени, скобки и прямоугольные матрицы) и заметки слайдов. MathML преобразуется в нативный OMML; [границы поддержки](formats.md#mathml).
- Индивидуальные сплошные заливки точек диаграмм (`series[].data_points[index].color_value` либо `color`) и отрыв секторов pie/doughnut (`explosion`, целое число от 0 до 400). Канонический `color_value` имеет приоритет перед `color`; при изменении только hex-цвета удалите прежний `color_value`. Индексы сохраняют позиции, включая пропуски данных. Некорректные индексы и значения отрыва диагностируются; прозрачность/ICC/blend пока приводятся к непрозрачному RGB с сообщением о потере. Два цикла JSON/PPTX проверяют повторное изменение этих свойств для столбчатой, круговой и кольцевой диаграммы.

Тесты изменяют текст, положение фигуры, ячейку и значения диаграммы и проверяют результат после двух циклов сохранения/чтения. Это проверка структуры и данных, не ручная приёмка в PowerPoint.

### Ограничения

Геометрия наборов диаграммы доступна для изменения через `gap_width` (0–500) и `overlap` (−100–100) у столбцов, `first_slice_angle` (0–360 градусов) у круговых/кольцевых диаграмм и `hole_size` (10–90 процентов) у кольцевых. Все значения целочисленные. Сохраняется логический флаг `vary_colors`; явные цвета рядов и точек остаются отдельными настройками. Для первого набора эти поля лежат в `chart`, для последующих — в `series[].plot`. При противоречивых настройках рядов одного набора используется первый ряд с сообщением о потере. Некорректные значения и свойства, неприменимые к типу диаграммы, диагностируются. Два JSON/PPTX-цикла проверяют изменение геометрии и независимость основной/дополнительной шкалы; это структурная проверка, не визуальная приёмка в Office.

Подписи данных сохраняют позицию, формат числа и связь с форматом источника, разделитель (включая пустой), показ значения, категории, имени ряда, процента, ключа легенды, размера пузырька и линий выноски. Настройки первого набора находятся в `chart.data_labels`, последующих наборов комбинированной диаграммы — в `series[].plot.data_labels`, а индивидуальные настройки ряда — в `series[].data_labels`. Явное `false` сохраняется; удаление настроек ряда возвращает наследование от набора. Настройки последующего набора повторены у его рядов: при редактировании меняйте их согласованно, экспорт использует первый ряд набора. Позиция и формат сохраняются даже без флагов показа. Произвольный текст, оформление и отдельные подписи конкретных точек пока не восстанавливаются; поведение подписей в офисной программе требует визуальной приёмки.

Исходные темы, мастера, макеты, анимации и непрозрачные части пакета не восстанавливаются. Сложное оформление таблиц/диаграмм упрощается, неподдержанные диаграммы заменяются текстовой сводкой, LaTeX и неподдержанные конструкции MathML — текстом. Потери отражаются в отчёте.

Смешанные XY/категориальные диаграммы, сочетания горизонтальных столбцов с линиями/областями или вертикальными столбцами, несовместимые наборы категорий и противоречивые описания plots пока переходят в явно диагностируемый текстовый fallback. Объёмные диаграммы поддерживаемых семейств преобразуются в плоские с сообщением о потере. Некорректные числовые данные и неполные XY-точки не заменяются нулями.

SVG не превращается в набор редактируемых фигур. Для SVG без растрового превью требуется совместимая программа просмотра; совместимость с конкретными версиями PowerPoint ещё не подтверждена. Сдвиговые трансформации (shear), возникающие при некоторых сочетаниях масштабирования и поворота групп, заменяются рамкой объекта с сообщением о потере. Сложные диаграммы не имеют полного обратного отображения. Автоматическая перемаршрутизация соединительных линий после перемещения связанных фигур требует проверки в офисных программах.

В режиме максимальной визуальной точности (`faithful`) новый экспортёр не предлагается. Полную сохранность оформления он не гарантирует.

Для текстовых заполнителей материализуется цепочка образец → макет → слайд: настройки шрифта, абзацев уровней 1–9 и текстового блока. Из `lstStyle` применяются общие и уровневые настройки; из текста родительского заполнителя — свойства первого абзаца соответствующего уровня. Локальные настройки слайда и отдельных фрагментов имеют приоритет. Связь с макетом определяется по `idx`, с образцом — по типу с нормализацией content/subTitle → body и ctrTitle → title; разные индексы образца и макета не мешают наследовать геометрию. Неоднозначный родитель не выбирается произвольно. Эти правила согласованы с [описанием заполнителей python-pptx](https://python-pptx.readthedocs.io/en/latest/user/placeholders-understanding.html).

Ссылки `+mj-lt` / `+mn-lt` на шрифты заголовков и основного текста разрешаются из темы образца. При отсутствии связи с темой образца используется тема презентации; `fontScheme` из themeOverride макета и затем слайда имеет приоритет. Явные имена шрифтов сохраняются. Подстановка применяется к фрагментам текста, ячейкам таблиц и явно заданному шрифту маркеров. Ссылки `ea`/`cs` разрешаются при наличии непустой соответствующей гарнитуры в схеме; языковой подбор по дополнительным записям `font script` пока не выполняется. Неразрешённая ссылка в текстовом фрагменте сохраняется с сообщением о потере `fonts` при экспорте PPTX. Структура схемы описана в [документации Microsoft](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.minorfont?view=openxml-3.0.1).

Полная поддержка темы, наследование всех эффектов и оформление самих макетов остаются открытыми. Файлы шрифтов не встраиваются; визуальная приёмка требует доступных гарнитур в офисной программе. Перенос параметров табуляции, автоподбора и вертикального письма проверен структурно; визуальная проверка их поведения в PowerPoint/LibreOffice ещё требуется. Для таблиц не восстанавливаются тема и условные стили, сложные заливки и эффекты. Явное оформление ячеек проверяется после изменения текста, заливки и высоты строки через два JSON/PPTX round-trip.

## MathML в редактируемых формулах PPTX


Экспортёр `DocumentModel → PPTX` преобразует `Formula(format=mathml)` в нативный Office Math (OMML). Поддерживаются отдельные формулы и формулы среди текстовых фрагментов абзаца. Исходная модель не изменяется; после чтения PPTX формула представлена как OMML.

Поддерживаемое подмножество Presentation MathML:

- `math`, `mrow`, `mi`, `mn`, `mo`, `mtext`;
- `mfrac`, `msub`, `msup`, `msubsup` с точным количеством аргументов;
- `msqrt`, `mroot`;
- `munder`, `mover`, `munderover`: нижние/верхние пределы и их сочетания;
- `mover accent="true"`: шляпка, тильда, стрелка вектора, одна/две точки над выражением; также над выражением с нижним пределом через `munderover`;
- черта сверху (`¯`, `‾`, U+0305) и снизу (`_`, U+0332), фигурная скобка сверху (`⏞`) и снизу (`⏟`) через `mover accent="true"` / `munder accentunder="true"`; подписи через внешний обычный предел;
- `mfenced`: односимвольные либо пустые границы, список разделителей;
- прямоугольные непустые `mtable` с `mtr` и `mtd`;
- `mstyle` и `mathvariant` у токенов: normal, italic, bold, bold-italic;
- `semantics`: используется первое выражение, дополнительные annotation/annotation-xml не переносятся.

Принимается пространство имён MathML либо XML без пространства имён. Используйте Unicode или числовые XML-ссылки для специальных символов. DTD и именованные сущности вроде `&alpha;` не поддерживаются. Ограничения входа: 1 МБ UTF-8, 4096 элементов, глубина 64.

Для обычных пределов задавайте `accent="false"` и/или `accentunder="false"`. Если атрибут опущен и аргумент содержит `mo`, экспортёр просит явно выбрать режим через диагностику потери: полный словарь операторов MathML пока не реализован. Без `mo` подразумевается обычный предел. Знак задаётся одним `mo`; допустим `stretchy="true"`, а фиксированный размер (`stretchy="false"`) не поддерживается. Базовые надстрочные акценты нормализуются в комбинируемые знаки Unicode для OMML. Черты сохраняются как `bar`, фигурные скобки — как `groupChr` с явным положением и вертикальным выравниванием. Перевёрнутые сочетания (например, `⏟` над выражением) и прочие нижние акценты не поддерживаются.

Неизвестные конструкции, атрибуты оформления, неверное число аргументов и некорректный XML приводят к замене всей формулы на `fallback_text` (при его отсутствии — исходную строку). Отчёт содержит потерю `formulas` с причиной и местом. LaTeX → OMML, Content MathML, остальные акценты, сложное оформление матриц и остальные варианты начертания пока не реализованы. Атрибут `display` принимается, но размещение на слайде задаётся блоком модели.

Тесты проверяют два цикла JSON/PPTX с изменением текста внутри нативной формулы между сохранениями, сохранение соседнего текста, отсутствие частично записанных формул при отказе и ограничение XML. HTML-предпросмотр сохраняет структуру корней, матриц, границы и базовое начертание OMML. Это структурная проверка: визуальная приёмка и ручное редактирование в PowerPoint/LibreOffice остаются открытыми.

Семантика конструкций описана в [спецификации MathML](https://www.w3.org/TR/MathML/mathml.html); структура Office Math — в [документации Microsoft для корней](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.math.radical?view=openxml-3.0.1).

Верхние и нижние пределы используют отдельные [объекты Office Math](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.math.limit?view=openxml-3.0.1); надстрочные знаки — [Accent](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.math.accent?view=openxml-3.0.1). Проверки различают направление пределов в HTML-предпросмотре и изменение знака после повторного сохранения PPTX.
