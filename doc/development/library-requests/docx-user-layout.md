# DOCX: текст и пагинация пользовательского документа

Владелец чтения/записи — OpenDoc Formats. TextAlchemy не исправляет документ вторым парсером и не меняет библиотеку. Это свидетельство для отдельной сессии владельца; исходный пользовательский документ не публикуется и не превращается в общедоступный fixture без отдельного разрешения.

## Проверенный случай

2026-10-08: TextAlchemy 0.2.0rc2, официальный OpenDoc Formats 0.10.0, OpenDoc Model 0.3.0; установленный Microsoft Word 16.0, build 16.0.17932. Пилотный `case-01` — DOCX с одной таблицей и одним заголовком уровня 3. Маршрут: настоящий Web API DOCX → JSON-модель → DOCX, правка отдельной копии в Word, сохранение/повторное открытие и следующий цикл.

| Наблюдение Word | Исходная рабочая копия | Результат первого цикла |
|---|---|---|
| Страницы `ComputeStatistics(2)` | 1 | 3 |
| Абзацы | 83 | 83 |
| Таблицы | 1 | 1 |
| Заголовки уровня 3 | 1 | 1 |
| Токены после нормализации пробельных символов | 370 | 369 |
| SHA-256 нормализованного текста | Исходный | Не совпадает |
| Диагностика маршрута | — | Нет сообщений; `lossless=true` |

Правка текста/ячейки, сохранение и повторное открытие в Word успешны в обоих циклах. Это отдельный положительный результат, который не отменяет отрицательные проверки текста и числа страниц. Во втором цикле число страниц остаётся 3; сравнение текста выполняется с предыдущей отредактированной копией, а не с исходником без QA-правки.

Нормализация заменяет маркер конца ячейки Word U+0007 пробелом, сжимает последовательности пробельных символов и убирает внешние пробелы. Разница числа токенов не равна числу потерянных слов и не устанавливает причину дефекта. Число страниц не является пиксельной оценкой; визуальная приёмка остаётся неизвестной.

## Ожидаемая граница

Опубликованный API должен сохранять заявленные свойства текста/таблицы/оформления либо явно диагностировать их упрощение. Нельзя объявлять геометрию принятой на основании успешного открытия и правки. TextAlchemy хранит исходные отчёты и отдельные наблюдения Word, не подменяет библиотечный `lossless` собственным обещанием.

Для расследования выделены независимые минимальные случаи на собственных строках ниже. Пользовательский текст не копируется в тесты. Оригиналы, рабочие копии, SHA-256, версии, Task ID и свидетельства остаются локально в `.textalchemy/acceptance/`; повторяемая проверка — `tools.acceptance.corpus` и `word-corpus.ps1`.

## Собственные минимальные случаи на 0.10.0

2026-10-08: `tests/corpus/docx_layout.py` независимо создаёт два DOCX без пользовательских
строк, изображений или исходного пакета. `tests/test_docx_layout_acceptance.py` выполняет
два реальных CLI-executor цикла DOCX → модель → DOCX через публичные API с `QualityPolicy(0)`.
Отдельные opt-in проверки открывают все три файла каждого случая read-only в Word 16.0,
build 16.0.17932, сравнивают входные SHA-256 до и после и сохраняют локальные свидетельства.

| Случай | Независимое наблюдение Word | Диагностика |
|---|---|---|
| `percentage-table` | Собственная таблица 20×3 с общей шириной 17 cm и колонками 10%/80%/10%. Ширины первой строки около 48.2/385.5/48.2 pt становятся 160.65/160.65/160.65 pt. Страницы 1 → 2 → 2; нормализованный текст совпадает | LOSS отсутствует; нулевой бюджет принимает оба цикла |
| `smart-tag` | Собственный текст `Before OwnSmartToken After`; средний токен находится в нативном `w:smartTag`. Word видит три токена, после первого результата — два; второй цикл сохраняет уже неполный текст | Импорт/экспорт не дают LOSS; нулевой бюджет принимает оба цикла |

Первый случай воспроизводит изменение колонок и пагинации, второй — потерю вложенного
текста. Они изолируют типы проблем, но не доказывают все причины исходного пользовательского
`case-01` и не заменяют его повторную приёмку. Тест читает все `w:t` независимо в QA:
`python-docx paragraph.text` сам не включает текст внутри smartTag и не подходит как эталон.
Приложение не получает новый XML-парсер или эвристику восстановления.

Ожидаемый контракт: сохранить относительные ширины выбранной таблицы и вложенный видимый
текст либо выдать расположенный LOSS до публикации. Сравнение с уже неполной моделью не
доказывает сохранность исходного документа. Приёмка исправления: собственные случаи плюс
разрешённый локальный пилот, два цикла, Word-текст, страницы, фактические ширины и неизменность
оригиналов. Точность единичного числа страниц зависит от программы/шрифтов; поддержка всего
DOCX этим не объявляется.

## Изолированная приёмка опубликованного 0.15.2

2026-10-08: официальный wheel Formats 0.15.2, SHA-256
`1330a8f1cb075c4074831c104c30c782149402f58ed67b8832bbc7b9f477126a`,
Model 0.3.0, Python 3.14.3 и установленный Word 16.0 build 16.0.17932.
Проверка выполнена в отдельном окружении с текущим исходным кодом приложения;
после этой проверки неизменённый выпуск подключён к основному окружению.
Повторены собственные Word-тесты и два пользовательских цикла через Web API (ASGI),
с настоящей Word-правкой между циклами. [Результаты интеграции](../../guide/verification.md#кандидат-docx-0152-word-ширины-и-smarttag).

Собственная таблица сохраняет `pct` 500/4000/500 и исходный текст в двух циклах.
Word читает одну страницу во всех трёх файлах; измеренные ширины первой строки
совпадают с исходными в пределах 0.5 pt. smartTag сохраняет все три токена и
исходную XML-оболочку, но диагностика `docx.smart-tags` имеет LOSS с причиной
`native-opaque`, а полнота семантической оценки остаётся ложной. Для двух циклов
явно разрешён один LOSS; бюджет 0 отдельно проверен: импорт отклонён, прежний
выходной файл сохранён. Непрозрачное сохранение не считается полной поддержкой smartTag.

Разрешённая локальная копия `case-01` прошла два цикла DOCX → JSON → DOCX,
настоящую правку, сохранение и повторное открытие в Word. Первый цикл:
страницы 1 → 1, токены 370 → 370, нормализованный текст совпадает. Второй читает
отредактированный результат: страницы 1 → 1, токены 374 → 374, текст снова совпадает.
Число таблиц и уровни заголовков совпадают в обоих циклах. SHA-256 источников сохранены;
необезличенные файлы и отчёты остаются только в `.textalchemy/acceptance/`.
Пиксельная приёмка, другие сложные объекты и семантическая роль заголовка этим не доказаны.
