# DjVu: декодирование UTF-8 и отсутствие текста

Контракт потребителя OF-03, 2026-10-08. Реализация и TODO принадлежат OpenDoc Formats; эта страница содержит воспроизводимое свидетельство приложения.

## Версии и разрешённый пример

OpenDoc Formats 0.6.0: SHA-256 wheel `699a2c555d12033380a712634fad8b39ee6c81f189c14f3b8946690eab7af532`. OpenDoc Model 0.3.0; Windows, Python 3.14, кодировка процесса cp1251, UTF-8 mode 0.

Официальный DjVuLibre 3.5.29 / DjView 4.12: [пакет и опубликованная сумма](https://sourceforge.net/projects/djvu/files/DjVuLibre_Windows/3.5.29%2B4.12/DjVuLibre-3.5.29_DjView-4.12_Setup.exe/download), SHA-256 `92233fbf891c63f3fb7a0b5e1ce108baa4c29a40c89a442d1313f883aae84670`. Из него извлечены командные инструменты в служебный каталог; установщик не запускался. Компоненты и лицензия не входят в релизный комплект приложения.

`tests/corpus/djvu_fixture.py` создаёт собственный двухстраничный пример средствами `c44`, `djvused`, `djvm`: белые изображения 320×180, скрытый текст «Пример №1 — Иванов Иван Иванович» и «Résumé: café, Straße, Ελληνικά». Второй вариант не содержит скрытого текста. Это тест слоя данных, а не OCR или визуальная приёмка скана. Воспроизведение не использует пользовательские документы.

## Наблюдения публичного API

1. В процессе cp1251 вызов `read_document(path, format_id="djvu")` для Unicode-примера даёт ошибку декодирования в потоке чтения subprocess; дальше возникает невалидная модель (`text: expected a str`). DjVuLibre выдаёт UTF-8, но ридер использует `text=True` без явно заданного UTF-8. В процессе с `PYTHONUTF8=1` обе строки сохраняются.
2. Для двухстраничного файла без текстового слоя DjVuLibre возвращает разделители страниц. Публичный импорт считает результат успешным; последующий TXT содержит ноль значимых символов. Это противоречит ожидаемому отказу «нет текстового слоя».

Повтор 2026-10-08 на официальном Formats 0.14.0 / Model 0.3.0: Python 3.14.3,
Windows cp1251, UTF-8 mode 0, тот же собственный двухстраничный fixture.
Два публичных импорта Unicode возвращают `success=False`, `document=None` и
`import.invalid-model` (`text: expected a string`); файл без текста по-прежнему
успешно импортируется, хотя текст модели пуст и диагностики отсутствуют. TextAlchemy блокирует оба
приложенческих маршрута ещё до импорта из-за требования UTF-8 окружения;
прежний результат и SHA-256 источников сохранены. Это повтор дефекта на
подключённой версии, а не приёмка ещё не опубликованного исправления.

## Ожидаемый контракт

| Случай | Результат API |
|---|---|
| UTF-8 скрытый текст, системная cp1251 | Точные Unicode-строки; декодирование задано адаптером независимо от кодировки вызывающего процесса |
| Нет текста / только разделители страниц | Явный отрицательный результат или документированная ошибка извлечения; не успешная пустая модель |
| Ошибка декодирования / повреждение / тайм-аут | Структурированная диагностика или документированная ошибка; не `None` внутри TextRun и не необработанный поток subprocess |
| Отмена | До чтения и после него соблюдается `ImportOptions.cancelled`; ограничение 30 секунд на текущий внешний вызов не выдаётся за немедленную отмену |

Текстовый маршрут не обещает координаты, изображения, оформление или OCR. Запрос не требует восстановления этих данных в данном срезе.

## Защита потребителя и приёмка

До исправления TextAlchemy разрешал маршрут только с `djvutxt` и UTF-8 кодировкой процесса; каталог предлагал `PYTHONUTF8=1` перед запуском. На официальном 0.15.1 требование UTF-8 снято после [приёмки Windows cp1251](../../guide/verification.md#djvu-0151-в-windows-cp1251). Пустой нормализованный текст отклоняется адаптером и защитой потребителя по публичной инспекции OpenDoc Model. Приложение не подменяет subprocess библиотеки, не декодирует выход самостоятельно и не правит установленный пакет.

Приёмка готового выпуска: реальные тесты `tests/convert/test_djvu_real.py` и `tests/test_web_djvu_real.py`, два запуска, Unicode, порядок текста, предупреждение области импорта, пустой слой, сохранение прежнего файла. Отдельно повторить на Windows cp1251 без флага UTF-8 после библиотечного исправления. Linux CI устанавливает `djvulibre-bin`; конфигурация CI не является свидетельством уже выполненного удалённого прогона.
