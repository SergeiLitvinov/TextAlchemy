# Document quality corpus

## Приёмка замены SVG в PDF

`tests/test_web_vector_fallback.py::vector_source` создаёт модель с одним SVG красного прямоугольника из открыто заданной строки в `tests/convert/test_pdf_resources.py`. Пользовательских данных и внешних файлов нет. Публичный адаптер выполняет реальный экспорт PDF. Проверяются потеря векторной редактируемости, два запуска Web-задачи и бюджеты `0`/`1`; исходная модель не меняется. Библиотека не предоставляет структурированную связь объектов для этой диагностики; приёмка её не придумывает. Визуальная идентичность SVG и PNG и правка в программе просмотра не проверяются.

## Приёмка цветовых диагностик

`tests/convert/test_color_budget.py::color_source` создаёт синтетическую модель через публичный API OpenDoc Model. Два текстовых фрагмента имеют одинаковый CMYK-цвет, условный идентификатор `Print-profile` и режим `multiply`. Документ не содержит пользовательских данных; идентификатор профиля не является встроенным реальным ICC-файлом. Пример проверяет поведение прикладного бюджета на диагностике готового адаптера: HTML — одно сообщение о профиле, DOCX/PDF — о профиле и наложении. Счётчик относится к сообщениям, а не к двум окрашенным фрагментам. Сохранность исходника, отказ публикации и повтор Web проверяются автоматически. Визуальный эталон цвета не задан.

The primary corpus is generated from source instead of storing opaque binary fixtures. Run:

```powershell
uv run python -m tests.corpus.scientific_report
uv run python -m tests.corpus.multiformat
```

The primary `scientific_report` fixture covers portrait and landscape sections,
named styles, numbering, headers and a page-number footer, hyperlinks, merged
tables, raster and SVG images, native OMML, and a footnote. Archive timestamps and
document metadata are fixed so identical dependencies produce identical bytes.

`multiformat.py` adds deterministic PDF, PPTX and EMF fixtures. It covers fixed PDF
page geometry, two-column text, tables, raster/vector commands, presentation text,
charts, tables, speaker notes and a native EMF package relationship. Nested chart
workbooks and outer OOXML archives have normalized timestamps, so two builds are
byte-identical.

`office/libreoffice-scientific-slides.pptx` is a committed compatibility profile
opened and re-saved by LibreOffice. Its producer/version, SHA-256 and expected WMF
part are recorded in `office/manifest.json`; the source content is generated by
`multiformat.py`.

Structural expectations live in `scientific_report.golden.json` and
`multiformat.golden.json`. Visual checks combine tolerant page occupancy bounds
with committed images under `visual/`. The perceptual regression normalizes page
size and antialiasing, then checks mean absolute similarity, difference-hash
distance and foreground intersection-over-union against explicit thresholds in
`visual/manifest.json`.

Regenerate page references only after reviewing an intentional visual change:

```powershell
uv run python -m tests.corpus.visual_references
```

`charts.py` builds a pure `DocumentModel` corpus of 14 rich chart fixtures (dual
axes, trendlines, error bars, per-point colors, combo, percent data labels).
Charts render deterministically through `pdf_writer` (fitz.Story) into PNG pages
compared perceptually against committed golden images in `visual/charts/`. The
per-chart pages and their thresholds live in `visual/charts/manifest.json`.

Regenerate chart references only after reviewing an intentional chart change:

```powershell
uv run python -m tests.corpus.charts
```

## DjVu text-layer corpus

`djvu_fixture.py` uses DjVuLibre `c44`, `djvused`, and `djvm` to build two original blank 320×180 pages with known Russian, French, German, and Greek hidden text. A second variant has no text layer. The content is generated in the test directory and has no third-party book or user data. It verifies Unicode extraction and page-text order; it is not an OCR, page-geometry, or visual fidelity reference. Real adapter and browser tests record the exact generated input/output hashes. Native tools remain external test prerequisites and are not included in the application archives.

Проверки обновления 0.8.2 используют собственные синтетические строки кириллицы и DOCX с созданной тестом вставкой (`tests/test_formats_release_integration.py`); пользовательских документов нет. Модель заголовков создаётся публичными типами и `set_heading` в `tests/convert/test_heading_budget.py`. ZIP/XML используется только в тесте для независимого свидетельства нативного Heading2, не в обработчиках приложения.

PDF-векторы в `tests/test_web_pdf_vectors.py` создаются тестом: кривая Безье, линия и собственный красный PNG. Источник не берётся из соседнего проекта. Независимые измерения PyMuPDF выполняются только в тестах; обработка файлов приложения остаётся у публичного адаптера.

## EPUB-структуры 0.10.0

`tests/test_web_epub_structures.py` создаёт собственный ZIP/XML EPUB через независимый fixture: таблица с объединением, вложенная таблица, смешанный текст и MathML; отдельный вариант содержит неверный rowspan. Документы пользователя и внешние ресурсы не используются. Созданные книги и результаты остаются во временном каталоге теста.

Для M8 пользователь разрешил чтение `C:/project/Учебные материалы`. Каталог является только источником: никаких копий, отчётов, преобразованных файлов или служебных материалов в него не записывать. Рабочие копии и свидетельства должны находиться в отдельном каталоге приёмки TextAlchemy. Состав выбранного корпуса и фактические результаты описаны ниже.

## Пользовательский пилот M8

2026-10-08 выполнено чтение разрешённого каталога: 27 828 файлов, включая 5 590 PDF, 3 052 DjVu, 2 106 DOC и 372 DOCX. Это инвентаризация расширений, а не утверждение поддержки или успешной обработки всех файлов. Три выбранных документа представлены локальными идентификаторами: `case-01` (DOCX с таблицей), `case-02` (DOCX с полями/text-boxes), `case-03` (связанный PDF). Имена, исходное содержимое и полные отчёты не публикуются.

Правила: только чтение исходного дерева; отдельные копии под `.textalchemy/acceptance/`; локальный Web, без отправки внешнему сервису; макросы в собственной Word COM-сессии отключены. Перед копированием и после каждого случая проверяется SHA-256 исходника. Предыдущая приёмка не перезаписывается. Необезличенные документы нельзя добавлять в Git/fixture или публичный выпуск. Собственные минимальные fixtures должны использовать новые строки и только необходимые свойства.

Критерии пилота: два цикла через реальные `/api/convert`/status/result, сохранённые отчёты и хеши; для DOCX — исходный инвентарь Word, правка абзаца и существующей ячейки, сохранение и повторное открытие, отдельное сравнение текста/пагинации/числа таблиц/уровней заголовков. Второй цикл читает именно отредактированную копию. Неизмеренные пиксельное сходство, память и полная семантическая приёмка остаются `null`. [Результаты](../guide/verification.md#пользовательский-пилот-m8).

Повторяемый инструмент:

```powershell
uv run --no-sync python -m tools.acceptance.corpus --manifest .textalchemy/acceptance/pilot-manifest.json --destination .textalchemy/acceptance/new-run --word
```

Манифест находится только локально: `source_root` и список `documents` с уникальными ASCII `id` и относительным `path`. Инструмент проверяет все пути до создания копий, запрещает выход из дерева источника и запись вне отдельного каталога приёмки приложения, принимает только loopback Web URL. Таймаут наблюдения сохраняет состояние задачи и не перезапускает её. JSON-свидетельство — `acceptance.json`; артефакты и правки Word лежат в каталогах случаев. Сбой проверки не считается приёмкой.

## PPTX в PowerPoint

Пилот расширен одним пользовательским PPTX (`pptx-01`), выбранным из разрешённого каталога без временных `~$`-файлов. Исходник содержит два слайда; PowerPoint-инвентарь и две правки выполнены на отдельных копиях. Имена/текст остаются локальными. `chart-01` — собственный файл с заголовком и столбчатой диаграммой, созданный независимым fixture; пользовательское содержимое не копируется.

```powershell
uv run --no-sync python -m tools.acceptance.corpus --manifest .textalchemy/acceptance/pptx-manifest.json --destination .textalchemy/acceptance/new-pptx-run --powerpoint
```

`powerpoint-corpus.ps1` открывает собственные копии без окна, отключает макросы на время QA и возвращает прежнюю настройку. Закрывает только свои презентации; существующий пользовательский PowerPoint не завершает. Контракт открытия — [Microsoft Presentations.Open](https://learn.microsoft.com/en-us/office/vba/api/powerpoint.presentations.open). Инвентарь ограничен верхним уровнем слайдов; текст хранится в свидетельстве как нормализованный SHA-256, а не открытый пользовательский текст. Первая доступная текстовая фигура получает новую QA-метку; первая доступная серия диаграммы меняет первое число на +1 и проверяется после открытия. Для отсутствующей диаграммы проверка остаётся `null`. [Матрица](../guide/verification.md#pptx-реальная-приёмка-в-powerpoint).

## Сканированный PDF и пользовательский DjVu

Пилот расширен тремя случаями: `scan-pdf-01` — двухстраничный скан без текста с изображением на каждой странице; `djvu-empty-01` — одностраничный DjVu без текстового слоя; `djvu-text-01` — 33-страничный DjVu с текстовым слоем. Выбор сделан после независимого чтения 35 PDF и 35 DjVu по возрастанию размера, начиная с файлов более 25 KB. Это выборка, не аудит всего каталога. Для сканированного PDF просмотрены обе страницы локального сравнения; изображение/подписи не публикуются.

Ожидания: PDF сохраняет число/размер страниц и положение изображений без объявления OCR; DjVu с текстом даёт тот же нормализованный полный текст; DjVu без слоя получает явный отказ с предложением распознавания. Целевые проверки: DjVuLibre 3.5.29 для исходного слоя, PyMuPDF для независимого измерения PDF; дальнейший пользовательский просмотр PDF планируется в Chromium PDF viewer и остаётся в M8.2. OCR, координаты DjVu и визуальная приёмка viewer пока не измерены. Отдельное наблюдение памяти процесса описано ниже.

Локальный манифест допускает `cycle_format: "txt"`: DjVu → модель → TXT → модель → TXT. Это два цикла обработки текста, не экспорт DjVu. В `acceptance.json` отдельно фиксируются `source_format` и `cycle_format`. Отсутствующий результат и отказ остаются отказом; `lossless` повторного TXT не распространяется на исходные страницы DjVu.

```powershell
uv run --no-sync python -m tools.acceptance.corpus --manifest .textalchemy/acceptance/scan-selection-20261008/manifest.json --destination .textalchemy/acceptance/new-scan-run
uv run --no-sync python -m tools.acceptance.scans --run-directory .textalchemy/acceptance/new-scan-run
```

Для текстового DjVu требуются DjVuLibre в PATH и UTF-8 процесс до исправления библиотечного ограничения. Измерения проверяют хеш копии/результата по Web-свидетельству, сравнивают полный текст без публикации содержания, рендерят все PDF-страницы и сохраняют отдельный `scan-measurements.json`. Повтор не перезаписывает этот файл: нужен новый каталог приёмки. [Результаты](../guide/verification.md#пользовательские-сканы-и-djvu), [собственный случай геометрии](library-requests/pdf-scan-geometry.md).

## Сложный PPTX и наблюдение памяти

2026-10-08 независимо прочитаны 40 пользовательских PPTX размером 100 KB–5 MB без `~$`. Выбран `pptx-complex-01`: 35 слайдов, 12 таблиц, 86 вложенных групп, 83 изображения и 560 текстовых фигур с учётом вложенности по python-pptx. Это описание выбранного входа, не доказательство экспорта всех этих объектов. PowerPoint COM измеряет отдельно верхний уровень; полные тексты, имена и пользовательские изображения не публикуются.

Два Web-цикла и две правки выполнены в PowerPoint 16.0 build 17932; оригинал сохранил SHA-256. Драйвер использует индекс фигуры в коллекции `Shapes`, не `ZOrderPosition`: позиция слоя может не совпадать с индексом. Ошибка нативного этапа сохраняет уже полученные Web-отчёты, хеш оригинала и тип отказа в `acceptance.json`, затем завершает прогон с ошибкой. Неполный прогон не является приёмкой.

В Windows инструмент поддерживает `--server-pid`: перед прогоном установите PID фактического слушателя Web-порта и отсутствие активных задач. Это явно выбранный процесс, не автоматически доказанное владение задачей. Пример для локального порта 8002:

```powershell
$acceptanceServerPid = (Get-NetTCPConnection -LocalPort 8002 -State Listen).OwningProcess
uv run --no-sync python -m tools.acceptance.corpus --manifest .textalchemy/acceptance/complex-pptx-selection-20261008/manifest.json --destination .textalchemy/acceptance/new-complex-run --powerpoint --server-pid $acceptanceServerPid
```

`tools.acceptance.memory` держит дескриптор одного процесса, фиксирует время его создания и опрашивает [Windows GetProcessMemoryInfo / WorkingSetSize](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters): рабочий набор физически отображённой памяти процесса. Номинальный интервал 20 ms; фиксируется также максимальный наблюдённый промежуток. Свидетельство включает baseline, `max_sampled_rss_bytes`, число выборок, продолжительность, ошибки и область от отправки запроса до скачивания результата. Между замерами пик может быть пропущен; `true_interval_peak_bytes` и прежний `peak_memory_bytes` остаются `null`. Дочерние движки, Word/PowerPoint, браузер и QA-клиент исключены; эксклюзивность задачи не утверждается.

Без PID память остаётся неизвестной; недоступный процесс/платформа и остановка процесса не подменяются нулём. Частичное наблюдение отмечается неполным и не скрывает ошибку операции. `tests/test_acceptance_memory.py` проверяет эти условия и реальное выделение памяти текущего Windows-процесса; `tests/test_user_corpus_acceptance.py` проверяет сохранение отчёта при нативном сбое. [Фактическая матрица](../guide/verification.md#сложный-pptx-и-память-web-процесса).

## Нативный рендер всех слайдов PowerPoint

Для `pptx-complex-01` выполнен отдельный read-only рендер в PowerPoint: 140 PNG, по 35 для исходника, первого результата, его PowerPoint-правки и второго результата. `powerpoint-corpus.ps1 -InspectOnly -RenderDirectory ...` использует [Slide.Export](https://learn.microsoft.com/en-us/office/vba/api/powerpoint.slide.export) с шириной 1280 px и высотой по пропорциям слайда; в данном случае 960 px. Это независимый QA, не новый движок конвертации приложения. Выход разрешён только в свежем подкаталоге `.textalchemy/acceptance/`; исходный каталог не используется для записи. Драйвер отключает макросы на время проверки, открывает источник read-only, закрывает свои презентации и возвращает настройку безопасности.

`target_program_check(..., program="powerpoint", render_directory=...)` принимает этот режим. JSON каждого рендера хранит версию/сборку Office, хеш входа, номера/хеши PNG, размеры и область `all-slides-before-QA-edit`. Локальные имена свидетелей: `source`, `cycle-1`, `edited-1`, `cycle-2`. Изображения и пользовательские данные не добавляются в Git или руководство.

```powershell
uv run --no-sync python -m tools.acceptance.powerpoint_visual --directory .textalchemy/acceptance/powerpoint-visual-20261008
```

Инструмент проверяет хеши PNG, полноту/порядок слайдов, совпадение версий PowerPoint и заявленных размеров. Он сравнивает исходник с первым результатом, а отредактированный первый результат — со вторым, не смешивая QA-правку с потерей конвертации. Сохраняет новый `visual-comparison.json`; повтор не перезаписывает свидетельство. Измеряются RGB-равенство, MAE и доля изменённых пикселей каждого слайда, без выдуманного процента качества и общей семантической оценки. Контрольные подмены/пропущенные слайды проверяются в `tests/test_powerpoint_visual.py`; реальные собственные chart/text и PNG проверяются в opt-in `tests/test_powerpoint_acceptance.py`. [Результат](../guide/verification.md#нативное-сравнение-всех-слайдов-pptx).

## Минимальные PPTX без пользовательского содержимого

`write_visual_presentation` в `tests/corpus/pptx_acceptance.py` независимо создаёт однослайдовые
`master-background`, `nested-group`, `freeform-axis-lines`, `freeform-line`, `table-theme` и
`table-style`. Они изолируют фон мастера, вложенные группы, два осевых свободных контура,
контрольный контур с ненулевым extent, наследуемый стиль таблицы и контрольное прямое оформление.
Это новые материалы проекта,
а не обезличенные копии учебных документов. Исходные binaries не хранятся в Git, генератор входит в sdist.

`tests/test_pptx_visual_acceptance.py` проверяет два публичных цикла, фактическое свойство фона,
число групп/контуров, текст и прямое оформление ячеек, диагностику и сохранение прежнего результата при строгом отказе.
Нативные тесты включаются переменной `TEXTALCHEMY_POWERPOINT_ACCEPTANCE=1` и выполняют read-only
рендер каждого из трёх файлов через установленный PowerPoint. Снимки и JSON создаются в свежем
UUID-каталоге `.textalchemy/acceptance/minimal-pptx-tests/`, хеши входов сверяются до и после.
Положительный тест известной потери означает воспроизводимость дефекта, а не приёмку оформления.
[Фактические результаты](../guide/verification.md#минимальные-pptx-фон-и-группы),
[контракт владельцу](library-requests/pptx-native-visual.md#собственные-минимальные-воспроизведения).

Свободные контуры создаются через независимый `build_freeform` python-pptx; горизонтальный
имеет нулевую высоту, вертикальный — нулевую ширину. Их видимость отдельно подтверждает PowerPoint,
а импорт текущего адаптера пропускает обе фигуры. Контрольный ломаный свободный контур с ненулевыми
extent сохраняется. Тема таблицы сравнивается с прямым заданием свойств ячеек, чтобы не переносить
вывод о потере наследуемого цвета на всё оформление PPTX. [Результаты](../guide/verification.md#pptx-свободные-линии-и-стиль-таблицы).

## Минимальные DOCX без пользовательского содержимого

`tests/corpus/docx_layout.py` создаёт два независимых случая: таблицу 20×3 с процентными
ширинами 10%/80%/10% и собственный текст внутри нативной обёртки `w:smartTag`. XML создаётся
только независимым fixture; приложение продолжает читать/писать DOCX через OpenDoc Formats.
Пользовательские строки и исходные пакеты не копируются в fixture или Git.

`tests/test_docx_layout_acceptance.py` проверяет два публичных цикла при нулевом бюджете LOSS,
колонки и полный собственный текст. Opt-in `TEXTALCHEMY_WORD_ACCEPTANCE=1` добавляет установленный
Word: read-only открытие трёх файлов, число страниц/токенов, SHA-256 нормализованного текста,
неизменность входов и нативные ширины ячеек первой строки. Новые UUID-каталоги свидетельств
находятся в `.textalchemy/acceptance/minimal-docx-tests/`; материал пользователя туда не нужен.

`word-corpus.ps1` теперь возвращает `inventory.table_geometry`: порядок таблиц, область
`first-row-native-cell-widths`, доступность и ширины в pt. Это не геометрия всех ячеек или страниц.
Если нерегулярная/объединённая строка недоступна в Word COM, остаются `available=false` и
`native-first-row-widths-unavailable`, без выдуманных размеров и остановки остальных измерений.
Зелёные проверки известных потерь подтверждают воспроизводимость; полное сохранение DOCX не принято.
